# Briefing design: how an orchestrator should write task briefs for cheaper sub-agents (Sonnet / Haiku)

Scope note: research date 2026-10-07. "Current generation" Anthropic docs cover Claude Fable 5.1, Mythos 5.1, Opus 5.5, Opus 5, Opus 4.8, Sonnet 5.5, Sonnet 5, Sonnet 4.6, Haiku 5.5, Haiku 4.5 ([Prompting best practices](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/claude-prompting-best-practices)). The Anthropic engineering posts are from 2024–2025 and the multi-agent research post was measured on **Claude Opus 4 lead + Sonnet 4 subagents**. That is older guidance, but it is still the main primary source on delegation. OpenAI GPT-4.1 guidance (April 2025) is flagged as an older, non-Claude analog. Primary texts were read in full: the multi-agent post, the context-engineering post, the cookbook prompts, the platform docs and the Claude Code docs. Pages were pulled with curl and HTML-to-text, and quotes were checked against that text. The coordinator's Playwright script was blocked by the permission classifier, so I fell back to curl and WebFetch. A few few-shot research papers were seen only as search snippets. Those are marked.

## 1. What Anthropic learned about delegating to sub-agents ("How we built our multi-agent research system")

### Takeaway
The four required parts of a brief are: objective, output format, tool and source guidance, and clear task boundaries. Short, vague briefs ("research the semiconductor shortage") caused misread tasks and duplicated searches. Anthropic fixed this by putting explicit effort-scaling rules, source-quality heuristics, search strategy (broad first, then narrow) and hard guardrails into the prompts. They framed prompts as "frameworks for collaboration" covering division of labor, approach and effort budgets, not rigid rules.

### Cited Findings
- **The four required parts:** "Each subagent needs an objective, an output format, guidance on the tools and sources to use, and clear task boundaries. Without detailed task descriptions, agents duplicate work, leave gaps, or fail to find necessary information." — [Anthropic, multi-agent research system (Jun 13 2025)](https://www.anthropic.com/engineering/multi-agent-research-system)
- **Vague-brief failure (before example):** "We started by allowing the lead agent to give simple, short instructions like 'research the semiconductor shortage,' but found these instructions often were vague enough that subagents misinterpreted the task or performed the exact same searches as other agents. For instance, one subagent explored the 2021 automotive chip crisis while 2 others duplicated work investigating current 2025 supply chains, without an effective division of labor." — [Anthropic](https://www.anthropic.com/engineering/multi-agent-research-system)
- **Effort scaling in the prompt:** "Agents struggle to judge appropriate effort for different tasks, so we embedded scaling rules in the prompts. Simple fact-finding requires just 1 agent with 3-10 tool calls, direct comparisons might need 2-4 subagents with 10-15 calls each, and complex research might use more than 10 subagents with clearly divided responsibilities." These guidelines "prevent overinvestment in simple queries, which was a common failure mode in our early versions." — [Anthropic](https://www.anthropic.com/engineering/multi-agent-research-system)
- **Early failure modes:** "spawning 50 subagents for simple queries, scouring the web endlessly for nonexistent sources, and distracting each other with excessive updates. Since each agent is steered by a prompt, prompt engineering was our primary lever." — [Anthropic](https://www.anthropic.com/engineering/multi-agent-research-system)
- **"Think like your agents":** simulations with the exact prompts and tools "immediately revealed failure modes: agents continuing when they already had sufficient results, using overly verbose search queries, or selecting incorrect tools." — [Anthropic](https://www.anthropic.com/engineering/multi-agent-research-system)
- **Tool heuristics put in prompts:** "examine all available tools first, match tool usage to user intent, search the web for broad external exploration, or prefer specialized tools over generic ones." Also: "an agent searching the web for context that only exists in Slack is doomed from the start." — [Anthropic](https://www.anthropic.com/engineering/multi-agent-research-system)
- **Search strategy:** "Agents often default to overly long, specific queries that return few results. We counteracted this tendency by prompting agents to start with short, broad queries, evaluate what's available, then progressively narrow focus." — [Anthropic](https://www.anthropic.com/engineering/multi-agent-research-system)
- **Thinking as a scratchpad:** the lead uses thinking for "assessing which tools fit the task, determining query complexity and subagent count, and defining each subagent's role"; "Subagents also plan, then use interleaved thinking after tool results to evaluate quality, identify gaps, and refine their next query." Extended thinking "improved instruction-following, reasoning, and efficiency." — [Anthropic](https://www.anthropic.com/engineering/multi-agent-research-system)
- **Parallelism:** "the lead agent spins up 3-5 subagents in parallel rather than serially; (2) the subagents use 3+ tools in parallel. These changes cut research time by up to 90% for complex queries." — [Anthropic](https://www.anthropic.com/engineering/multi-agent-research-system)
- **Source quality:** "human testers noticed that our early agents consistently chose SEO-optimized content farms over authoritative but less highly-ranked sources like academic PDFs or personal blogs. Adding source quality heuristics to our prompts helped resolve this issue." — [Anthropic](https://www.anthropic.com/engineering/multi-agent-research-system)
- **Heuristics over rigid rules, plus guardrails:** "Our prompting strategy focuses on instilling good heuristics rather than rigid rules… We also proactively mitigated unintended side effects by setting explicit guardrails to prevent the agents from spiraling out of control." — [Anthropic](https://www.anthropic.com/engineering/multi-agent-research-system)
- **Prompts as collaboration frameworks:** "small changes to the lead agent can unpredictably change how subagents behave… the best prompts for these agents are not just strict instructions, but frameworks for collaboration that define the division of labor, problem-solving approaches, and effort budgets." — [Anthropic](https://www.anthropic.com/engineering/multi-agent-research-system)
- **Letting agents improve prompts:** "Claude 4 models can be excellent prompt engineers. When given a prompt and a failure mode, they are able to diagnose why the agent is failing and suggest improvements." A tool-testing agent that rewrote tool descriptions gave "a 40% decrease in task completion time for future agents." — [Anthropic](https://www.anthropic.com/engineering/multi-agent-research-system)
- **Eval rubric (usable as acceptance criteria for sub-agent output):** "factual accuracy (do claims match sources?), citation accuracy (do the cited sources match the claims?), completeness (are all requested aspects covered?), source quality (did it use primary sources over lower-quality secondary sources?), and tool efficiency (did it use the right tools a reasonable number of times?)". A single LLM-judge call outputting 0.0–1.0 scores and pass/fail "was the most consistent and aligned with human judgements". Start with "about 20 queries"; "A prompt tweak might boost success rates from 30% to 80%." — [Anthropic](https://www.anthropic.com/engineering/multi-agent-research-system)
- **Performance and cost:** Opus 4 lead + Sonnet 4 subagents "outperformed single-agent Claude Opus 4 by 90.2% on our internal research eval". "Token usage by itself explains 80% of the variance" on BrowseComp, with tool calls and model choice as the other two factors (95% total). Agents use about 4× the tokens of chat and multi-agent systems about 15×. "Upgrading to Claude Sonnet 4 is a larger performance gain than doubling the token budget on Claude Sonnet 3.7." — [Anthropic](https://www.anthropic.com/engineering/multi-agent-research-system)
- **Write outputs to storage to avoid the "game of telephone":** "Subagents call tools to store their work in external systems, then pass lightweight references back to the coordinator. This prevents information loss during multi-stage processing and reduces token overhead… works particularly well for structured outputs." — [Anthropic, appendix](https://www.anthropic.com/engineering/multi-agent-research-system)
- **Fit:** multi-agent "excel especially for breadth-first queries that involve pursuing multiple independent directions simultaneously". Example: S&P 500 IT board members, where the single agent "failed to find the answer with slow, sequential searches." — [Anthropic](https://www.anthropic.com/engineering/multi-agent-research-system)
- **Limits of synchronous runs:** "the lead agent can't steer subagents, subagents can't coordinate, and the entire system can be blocked while waiting for a single subagent." — [Anthropic](https://www.anthropic.com/engineering/multi-agent-research-system)

### Inferences
- A per-country fan-out (195 Sonnet agents) is the "breadth-first" case this architecture suits. The reported failure modes (misread task, duplicated or overlapping work, endless searching, low-quality sources, continuing after enough results) are the ones you would expect from a short, templated brief that lacks an output schema, a source policy and a stopping rule.
- Anthropic's own gains were measured with **Sonnet as the subagent model**. So "Sonnet is too weak" is probably not the main cause. The brief, the tools and the stopping rules are the first things to fix.

### Gaps
- Anthropic does not publish example briefs that failed and then succeeded for the same query, beyond the semiconductor example. The post gives no numbers comparing brief styles for Sonnet versus Opus subagents.

## 2. Anthropic's current prompt-engineering docs (Claude 4.x / 5.x): explicitness, context, examples, XML, format, literalism, and Sonnet/Haiku specifics

### Takeaway
Current docs treat Claude as a "brilliant but new employee who lacks context". They advise explaining *why*, giving 3–5 relevant and diverse examples in tags, using XML sections, and saying what to do rather than what not to do. The cheaper models are documented as **more literal and more likely to stop early, skip searches, skip verification, and skip thinking at low or medium effort**. Each of these has a tested prompt fix. Frontier Opus 5 has the opposite problems: it over-verifies, widens scope and over-delegates. Briefs therefore need to be model-aware.

### Cited Findings
**General (all current models)**
- "Think of Claude as a brilliant but new employee who lacks context on your norms and workflows. The more precisely you explain what you want, the better the result." **Golden rule:** "Show your prompt to a colleague with minimal context on the task and ask them to follow it. If they'd be confused, Claude will be too." — [Prompting best practices](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/claude-prompting-best-practices)
- "Be specific about the desired output format and constraints. Provide instructions as sequential steps using numbered lists or bullet points when the order or completeness of steps matters." "If you want 'above and beyond' behavior, explicitly request it." — [Prompting best practices](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/claude-prompting-best-practices)
- **Give the reason (before/after):** "NEVER use ellipses" becomes "Your response will be read aloud by a text-to-speech engine, so never use ellipses since the text-to-speech engine will not know how to pronounce them." The doc adds: "Claude is smart enough to generalize from the explanation." — [Prompting best practices](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/claude-prompting-best-practices)
- **Examples:** "Examples are one of the most reliable ways to steer Claude's output format, tone, and structure." Make them "Relevant… Diverse: Cover edge cases and vary enough that Claude doesn't pick up unintended patterns… Structured: Wrap examples in `<example>` tags". "Include 3–5 examples for best results." — [Prompting best practices](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/claude-prompting-best-practices)
- **XML:** "Wrapping each type of content in its own tag (for example, `<instructions>`, `<context>`, `<input>`) reduces misinterpretation… Use consistent, descriptive tag names." — [Prompting best practices](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/claude-prompting-best-practices)
- **Format control:** "Tell Claude what to do instead of what not to do". Instead of "Do not use markdown", say "Your response should be composed of smoothly flowing prose paragraphs." "Match your prompt style to the desired output… removing markdown from your prompt can reduce the volume of markdown in the output." — [Prompting best practices](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/claude-prompting-best-practices)
- **Long context:** put long documents at the top and the query at the end. "Queries at the end can improve response quality by up to 30 percent in tests, especially with complex, multidocument inputs." — [Prompting best practices](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/claude-prompting-best-practices)
- **Action verbs:** "Claude's latest models are trained for precise instruction following… If you say 'can you suggest some changes,' Claude will sometimes provide suggestions rather than implementing them." — [Prompting best practices](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/claude-prompting-best-practices)
- **Research tasks:** "Provide clear success criteria: Define what constitutes a successful answer… Encourage source verification: Ask Claude to verify information across multiple sources." Sample prompt: "As you gather data, develop several competing hypotheses. Track your confidence levels in your progress notes to improve calibration. Regularly self-critique your approach and plan." — [Prompting best practices](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/claude-prompting-best-practices)
- **Damping over-delegation (orchestrator side):** "Use subagents when tasks can run in parallel, require isolated context, or involve independent workstreams that don't need to share state. For simple tasks, sequential operations, single-file edits, or tasks where you need to maintain context across steps, work directly rather than delegating." — [Prompting best practices](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/claude-prompting-best-practices)
- **Model-specific caveat:** "Where a technique names a specific model, treat it as measured on that model and re-check it against your own evals before applying it to another." — [Prompting best practices](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/claude-prompting-best-practices)
- **Anti-laziness prompting is now harmful on frontier models:** "If your prompts previously encouraged the model to be more thorough or use tools more aggressively, dial back that guidance… may overtrigger"; "Instructions like 'If in doubt, use [tool]' will cause overtriggering." — [Prompting best practices](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/claude-prompting-best-practices)

**Sonnet 5 / 5.5 (likely sub-agent tier)**
- **Literalism:** "Claude Sonnet 5 interprets prompts literally and explicitly, particularly at lower effort levels. It does not silently generalize an instruction from one item to another, and it does not infer requests you didn't make… If you need Claude to apply an instruction broadly, state the scope explicitly (for example, 'Apply this formatting to every section, not just the first one')." — [Prompting Claude Sonnet 5](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/prompting-claude-sonnet-5)
- "Positive examples showing how Claude can communicate with the appropriate level of concision tend to be more effective than negative examples or instructions that tell the model what not to do." — [Prompting Claude Sonnet 5](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/prompting-claude-sonnet-5)
- "With thinking disabled, the model is less likely to reach for tools or consider searching… if you find that the model is not using your web search tools, clearly describe why and how it should." — [Prompting Claude Sonnet 5](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/prompting-claude-sonnet-5)
- **Sonnet 5.5 effort:** "For agentic coding and multistep tool use, start at `medium` for well-specified tasks and move to `high` for harder or longer ones." At low or medium, "on long agentic tasks, it's more likely to stop and check in with the user before it finishes." "For the hardest long-horizon work, an Opus model is the better choice." — [Prompting Claude Sonnet 5.5](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/prompting-claude-sonnet-5-5)
- **Sonnet 5.5 persistence and scope prompt:** "Keep working until everything the user asked for is done, and only stop to ask when you can't go on without the user or before a risky step. When the work the user asked for is done and checked, stop and report. Don't add features, tests, files, docs or refactors that weren't asked for. If you think one would help, mention it at the end instead of doing it." — [Prompting Claude Sonnet 5.5](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/prompting-claude-sonnet-5-5)
- **Sonnet 5.5 skips searching:** it "sometimes answers from its training knowledge when a web search would catch details that have changed." Fix: "check your prompt for language that discourages tool use, such as 'only use tools when strictly necessary' or 'minimize tool calls', and remove it". Then add: "Use the search tool to check specifics that may have changed since your training… even when you feel confident. For researched work such as a report or a comparison, gather current sources rather than writing from your training knowledge." — [Prompting Claude Sonnet 5.5](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/prompting-claude-sonnet-5-5)
- **Sonnet 5.5 JSON reasoning:** "On tasks like these [totaling figures, applying a rule, ranking], the model often answers without thinking first, particularly at `low` and `medium` effort." Fix: add "Think the problem through before you answer." When JSON is requested without structured outputs, "Parse the last JSON value in the response… treat a response whose `stop_reason` is `"max_tokens"` as failed… retry once if it doesn't [have expected fields]." — [Prompting Claude Sonnet 5.5](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/prompting-claude-sonnet-5-5)
- **Sonnet 5.5 at xhigh/max** launches its own review rounds and reviewer subagents. A "stop and report" prompt "cut session cost by about a third, with no change in quality." — [Prompting Claude Sonnet 5.5](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/prompting-claude-sonnet-5-5)

**Haiku 5.5 (cheapest tier)**
- **Date grounding:** "When you give Claude Haiku 5.5 a search tool, also give it today's date. In Anthropic's testing, this grounded the model's answers in recent search results." — [Prompting Claude Haiku 5.5](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/prompting-claude-haiku-5-5)
- **Search nudge (tested):** "Your training data ends well before today's date. Records, office holders, prices, versions, rules and anything 'latest' may have changed since then, so search for those before you answer, even when you feel sure. Facts that can't change need no search…" This "raised the search rate on questions whose answers had changed" and added unneeded searches in "only 0–3 percent of tries". Skipping searches happens "most at `low` effort and with long system prompts." — [Haiku 5.5](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/prompting-claude-haiku-5-5)
- **Blanket rules backfire:** "Avoid blanket instructions such as 'search for any present-day factual question, regardless of how confident you are.' In Anthropic's testing, that instruction made the model search on half of the prompts that needed no search. It didn't produce more correct answers." — [Haiku 5.5](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/prompting-claude-haiku-5-5)
- **Early stopping:** "With a short system prompt, Claude Haiku 5.5 rarely stops before the work is done. With a long coding-agent system prompt at `low` effort, it sometimes stops early and hands the task back." Moving from low to medium "roughly halved early stopping. It also more than doubled the output tokens." — [Haiku 5.5](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/prompting-claude-haiku-5-5)
- **JSON plus tools with thinking off:** Haiku "might skip a tool call it needs when you also request JSON output". Fix line: "The JSON output format applies to your final answer only. When you need a tool, call it first… and write the JSON once you have the results." — [Haiku 5.5](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/prompting-claude-haiku-5-5)
- **Verification:** "At `low` and `medium` effort, Claude Haiku 5.5 sometimes reports a code change as done without running a check." The fix is a verification paragraph, which also requires saying which check was not run and why. — [Haiku 5.5](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/prompting-claude-haiku-5-5)
- **Asking it to think less doesn't work:** "telling the model in the prompt to answer directly didn't stop it from thinking". Lower the effort instead. — [Haiku 5.5](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/prompting-claude-haiku-5-5)

**Opus 5 (orchestrator tier): contrast**
- "Claude Opus 5 verifies its own work without being told to… remove [explicit verification instructions]: instructions like these cause over-verification." It "can also expand the scope of a task." Avoid "double-check your answer" style instructions. — [Prompting Claude Opus 5](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/prompting-claude-opus-5)
- "Claude Opus 5 delegates to subagents more readily than prior models… multiplies cost and time when applied to small tasks." Sample: "Delegate to a subagent only for large tasks that are genuinely independent and parallelizable… If one subagent can complete the task, use one rather than several, and keep spawn counts low." Deterministic caps: `CLAUDE_CODE_MAX_SUBAGENT_SPAWN_DEPTH`, `CLAUDE_CODE_MAX_CONCURRENT_SUBAGENTS`, and SDK `max_budget_usd`. — [Prompting Claude Opus 5](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/prompting-claude-opus-5)
- "Files that Claude Opus 5 writes to disk… are often longer than on prior models". Suggested line: "Match the length of written documents to what the task needs." — [Prompting Claude Opus 5](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/prompting-claude-opus-5)

### Inferences
- **Frontier and cheap models need opposite steering.** Opus 5 needs restraint (don't over-verify, don't widen scope, don't over-delegate). Sonnet and Haiku at lower effort need *push*: keep going until done, search for changeable facts, verify, think before writing JSON. They also need explicitly stated scope because of their literalism. An orchestrator writing briefs "the way it would want to be briefed" may leave out exactly the push the cheaper model needs. The skill should tell the orchestrator to add these lines explicitly for Sonnet and Haiku sub-agents.
- Literalism means "do X for each indicator" must enumerate the indicators. "Like the example" will not be generalized beyond what the brief states. Any rule meant to apply to all fields or sections must say "all".
- Anti-patterns to remove from cheaper-model briefs: "minimize tool calls" and "only search if strictly necessary" (these suppress needed searches on Sonnet 5.5), and blanket "always search everything" (wasteful on Haiku, with no accuracy gain). Prefer a *calibrated* rule: search for anything that can change, such as office holders, statistics, laws and prices.
- Tested phrasings worth reusing verbatim come from the Sonnet 5.5 persistence/stop prompt, the Haiku 5.5 date-plus-search nudge, "Think the problem through before you answer", and the Haiku JSON-after-tools line.

### Gaps
- I did not find any Anthropic doc that gives guidance specifically for *the orchestrator-to-subagent task message* by model tier. The model pages address system prompts generally. Whether Claude Code lets the orchestrator set effort per sub-agent invocation was not documented in the pages I read.
- The Opus 4.8 "subagent control" section was not read in full.

## 3. Context-engineering posts applied to briefing ("Effective context engineering", "Writing tools for agents", "Building effective agents", Claude Code best practices)

### Takeaway
Write the brief at the "right altitude": concrete signals and heuristics, not brittle if/else logic, and not vague guidance that "falsely assumes shared context". Use the minimal set of high-signal tokens (minimal does not mean short). Organize it into labeled sections, use a few canonical examples rather than long edge-case lists, pass references (paths or URLs) rather than bulk data, and ask for a condensed return of about 1–2k tokens.

### Cited Findings
- **Right altitude:** prompts should present "ideas at the right altitude… At one extreme, we see engineers hardcoding complex, brittle logic in their prompts… At the other extreme, engineers sometimes provide vague, high-level guidance that fails to give the LLM concrete signals for desired outputs or falsely assumes shared context. The optimal altitude strikes a balance: specific enough to guide behavior effectively, yet flexible enough to provide the model with strong heuristics." — [Anthropic, Effective context engineering (Sep 29 2025)](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)
- **Sections:** "We recommend organizing prompts into distinct sections (like `<background_information>`, `<instructions>`, `## Tool guidance`, `## Output description`, etc)… although the exact formatting of prompts is likely becoming less important as models become more capable." — [Context engineering](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)
- **Minimal ≠ short:** "strive for the minimal set of information that fully outlines your expected behavior. (Note that minimal does not necessarily mean short; you still need to give the agent sufficient information up front…)" Also: "start by testing a minimal prompt with the best model available… then add clear instructions and examples to improve performance based on failure modes found during initial testing." — [Context engineering](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)
- **Examples, not laundry lists:** "teams will often stuff a laundry list of edge cases into a prompt… We do not recommend this. Instead, we recommend working to curate a set of diverse, canonical examples that effectively portray the expected behavior… For an LLM, examples are the 'pictures' worth a thousand words." — [Context engineering](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)
- **Condensed handoff:** "Each subagent might explore extensively, using tens of thousands of tokens or more, but returns only a condensed, distilled summary of its work (often 1,000-2,000 tokens)." — [Context engineering](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)
- **Just-in-time references:** agents "maintain lightweight identifiers (file paths, stored queries, web links, etc.) and use these references to dynamically load data into context at runtime". "Without proper guidance, an agent can waste context by misusing tools, chasing dead-ends, or failing to identify key information." — [Context engineering](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)
- **Context rot:** "as the number of tokens in the context window increases, the model's ability to accurately recall information from that context decreases… Context, therefore, must be treated as a finite resource with diminishing marginal returns." — [Context engineering](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)
- **Tool sets:** "If a human engineer can't definitively say which tool should be used in a given situation, an AI agent can't be expected to do better." — [Context engineering](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)
- **Agent-computer interface (ACI):** "Put yourself in the model's shoes… A good tool definition often includes example usage, edge cases, input format requirements, and clear boundaries from other tools." "Think of this as writing a great docstring for a junior developer on your team." "Poka-yoke your tools." Example: requiring absolute filepaths made the model use the tool "flawlessly". — [Anthropic, Building effective agents (Dec 2024)](https://www.anthropic.com/research/building-effective-agents)
- **Separate calls for separate concerns:** "For complex tasks with multiple considerations, LLMs generally perform better when each consideration is handled by a separate LLM call, allowing focused attention on each specific aspect." Agents should get "'ground truth' from the environment at each step"; it is "common to include stopping conditions (such as a maximum number of iterations)". — [Building effective agents](https://www.anthropic.com/research/building-effective-agents)
- **Date bias in queries:** "Claude was needlessly appending 2025 to the tool's query parameter, biasing search results and degrading performance (we steered Claude in the right direction by improving the tool description)." — [Anthropic, Writing tools for agents](https://www.anthropic.com/engineering/writing-tools-for-agents)
- **Steer via instructions:** "You can directly encourage agents to pursue more token-efficient strategies, like making many small and targeted searches instead of a single, broad search." Also, reasoning/feedback blocks requested "before tool call and response blocks may increase LLMs' effective intelligence by triggering chain-of-thought (CoT) behaviors." — [Writing tools for agents](https://www.anthropic.com/engineering/writing-tools-for-agents)
- **Specific-context before/after table:** "add tests for foo.py" becomes "write a test for foo.py covering the edge case where the user is logged out. avoid mocks." "fix the login bug" becomes "users report that login fails after session timeout. check the auth flow in src/auth/, especially token refresh. write a failing test that reproduces the issue, then fix it". The guiding line: "Claude can infer intent, but it can't read your mind. Reference specific files, mention constraints, and point to example patterns." — [Claude Code best practices](https://code.claude.com/docs/en/best-practices)
- **Self-contained specs:** "The most useful specs are self-contained: they name the files and interfaces involved, state what is out of scope, and end with an end-to-end verification step that proves the feature works. Time spent making the spec precise pays off more than time spent watching the implementation." — [Claude Code best practices](https://code.claude.com/docs/en/best-practices)
- **Give it a check:** "Claude stops when the work looks done. Without a check it can run, 'looks done' is the only signal available." Also: "Have Claude show evidence rather than asserting success." — [Claude Code best practices](https://code.claude.com/docs/en/best-practices)
- **Instruction dilution:** "If Claude keeps doing something you don't want despite having a rule against it, the file is probably too long and the rule is getting lost." — [Claude Code best practices](https://code.claude.com/docs/en/best-practices)

### Inferences
- In a fan-out, the "falsely assumes shared context" failure is built in: the orchestrator knows the user's goal, definitions and conventions, and the sub-agent knows none of them. A brief at the right altitude names the concrete fields, sources and stop rule. It explains *why* (what the aggregate will be used for) so the sub-agent can handle cases the orchestrator didn't foresee, instead of listing every edge case.
- "Give it a check" carries over to research: the brief can include a self-check list (every required field filled or explicitly marked not found, each value has a URL, dates inside the window). The sub-agent runs it before returning.

### Gaps
- None of these posts quantify the best brief length. The 1–2k-token figure is for the *return*, not the brief.

## 4. What a brief must specify: objective/why, scope (and non-scope), output schema, source policy, tools, effort budget and stopping, missing data, confidence/citations

### Takeaway
Anthropic's open-sourced lead-agent prompt gives an explicit checklist for every delegation. The sub-agent prompt adds the budget, stop and source-quality rules. Together with the docs above, a complete brief covers: (1) one core objective, (2) background and why, (3) key questions, (4) explicit boundaries and non-goals, (5) the output format/schema, (6) a source policy (what counts as reliable, what to avoid), (7) which tools to use and how, (8) a tool-call budget plus a stop rule, (9) how to report conflicts and gaps, and (10) the current date. Missing data must be flagged, not filled in.

### Cited Findings
- **Anthropic's per-delegation checklist (lead prompt):** "All instructions for subagents should include the following as appropriate: Specific research objectives, ideally just 1 core objective per subagent. Expected output format - e.g. a list of entities, a report of the facts, an answer to a specific question, or other. Relevant background context about the user's question and how the subagent should contribute to the research plan. Key questions to answer as part of the research. Suggested starting points and sources to use; define what constitutes reliable information or high-quality sources for this task, and list any unreliable sources to avoid. Specific tools that the subagent should use… If needed, precise scope boundaries to prevent research drift." — [Anthropic cookbook, research_lead_agent.md](https://github.com/anthropics/claude-cookbooks/blob/main/patterns/agents/prompts/research_lead_agent.md)
- **Aggregate test:** "Make sure that IF all the subagents followed their instructions very well, the results in aggregate would allow you to give an EXCELLENT answer to the user's question - complete, thorough, detailed, and accurate." — [research_lead_agent.md](https://github.com/anthropics/claude-cookbooks/blob/main/patterns/agents/prompts/research_lead_agent.md)
- **Non-overlap:** "Define extremely clear, crisp, and understandable boundaries between sub-topics to prevent overlap." Also: "Avoid overlap between subagents - every subagent should have distinct, clearly separate tasks." — [research_lead_agent.md](https://github.com/anthropics/claude-cookbooks/blob/main/patterns/agents/prompts/research_lead_agent.md)
- **Density:** "In communicating with subagents, maintain extremely high information density while being concise - describe everything needed in the fewest words possible." — [research_lead_agent.md](https://github.com/anthropics/claude-cookbooks/blob/main/patterns/agents/prompts/research_lead_agent.md)
- **Source guidance per task:** "When giving instructions to subagents, also think about what sources might be high-quality for their tasks, and give them some guidelines on what sources to use and how they should evaluate source quality for each task." — [research_lead_agent.md](https://github.com/anthropics/claude-cookbooks/blob/main/patterns/agents/prompts/research_lead_agent.md)
- **Budget plus stop rule (sub-agent prompt):** "determine a 'research budget' - roughly how many tool calls… simpler tasks… under 5 tool calls, medium tasks… 5 tool calls, hard tasks… about 10 tool calls, and very difficult or multi-part tasks… up to 15 tool calls. Stick to this budget." Hard ceiling: "stay under a limit of 20 tool calls and under about 100 sources… whenever you get to around 15 tool calls or 100 sources, make sure to stop gathering sources… Avoid continuing to use tools when you see diminishing returns." Also: "As soon as you have the necessary information, complete the task rather than wasting time." — [Anthropic cookbook, research_subagent.md](https://github.com/anthropics/claude-cookbooks/blob/main/patterns/agents/prompts/research_subagent.md)
- **Source-quality heuristics (sub-agent prompt):** watch for speculation ("verbs like 'could' or 'may', narrative driven speculation with future tense, quoted superlatives, financial projections") and note it "rather than accepting these events as having happened". Watch for "news aggregators rather than original sources… false authority, pairing of passive voice with nameless sources, general qualifiers without specifics, unconfirmed reports, marketing language… spin… cherry-picked data". "Flag these issues when returning your report… rather than blindly presenting all results as established facts." — [research_subagent.md](https://github.com/anthropics/claude-cookbooks/blob/main/patterns/agents/prompts/research_subagent.md)
- **Conflicts go back to the lead:** "When encountering conflicting information, prioritize based on recency, consistency with other facts, the quality of the sources… If unable to reconcile facts, include the conflicting information in your final task report for the lead researcher to resolve." — [research_subagent.md](https://github.com/anthropics/claude-cookbooks/blob/main/patterns/agents/prompts/research_subagent.md)
- **What to keep:** facts that are "Significant… Important… Precise (specific facts, numbers, dates…)… High-quality". "Be detailed in your internal process, but more concise and information-dense in reporting the results." — [research_subagent.md](https://github.com/anthropics/claude-cookbooks/blob/main/patterns/agents/prompts/research_subagent.md)
- **Query hygiene:** "Use moderately broad queries rather than hyper-specific ones. Keep queries shorter… under 5 words. If specific searches yield few results, broaden slightly." "NEVER repeatedly use the exact same queries." Also: "ALWAYS use `web_fetch` to get the complete contents of websites… when following up on web_search results". — [research_subagent.md](https://github.com/anthropics/claude-cookbooks/blob/main/patterns/agents/prompts/research_subagent.md)
- **Date in the prompt:** the sub-agent prompt opens with "The current date is {{.CurrentDate}}." — [research_subagent.md](https://github.com/anthropics/claude-cookbooks/blob/main/patterns/agents/prompts/research_subagent.md). The Haiku 5.5 doc independently found that giving the date grounds search answers. — [Haiku 5.5](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/prompting-claude-haiku-5-5)
- **Missing info and edge cases (OpenAI):** "Capture edge cases… how to proceed when a user provides incomplete information… includes instructions on how to handle them with conditional steps or branches such as an alternative step if a required piece of info is missing." "Define clear actions: Make sure every step in your routine corresponds to a specific action or output." — [OpenAI, A practical guide to building agents](https://cdn.openai.com/business-guides-and-resources/a-practical-guide-to-building-agents.pdf)
- **"Must" rules create fabrication pressure:** "if told 'you must call a tool before responding to the user,' models may hallucinate tool inputs or call the tool with null values if they do not have enough information. Adding 'if you don't have enough information to call the tool, ask the user for the information you need' should mitigate this." — [OpenAI GPT-4.1 prompting guide (Apr 2025; older, non-Claude)](https://cookbook.openai.com/examples/gpt4-1_prompting_guide)
- **Don't guess:** "If you are not sure about file content or codebase structure… use your tools to read files and gather the relevant information: do NOT guess or make up an answer." — [GPT-4.1 guide](https://cookbook.openai.com/examples/gpt4-1_prompting_guide). Claude analog: "Never speculate about code you have not opened… give grounded and hallucination-free answers." — [Prompting best practices](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/claude-prompting-best-practices)
- **Confidence tracking:** "Track your confidence levels in your progress notes to improve calibration." — [Prompting best practices](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/claude-prompting-best-practices)
- **Separate citation concern:** Anthropic's lead agent was told "Do not include ANY Markdown citations, a separate agent will be responsible for citations". The CitationAgent must keep the text "100% identical, only add citations" and "ONLY add citations where the source documents directly support claims". — [research_lead_agent.md](https://github.com/anthropics/claude-cookbooks/blob/main/patterns/agents/prompts/research_lead_agent.md); [citations_agent.md](https://github.com/anthropics/claude-cookbooks/blob/main/patterns/agents/prompts/citations_agent.md)
- **Effort budget as a frontier of quality vs. cost:** token usage explains about 80% of performance variance. — [Anthropic](https://www.anthropic.com/engineering/multi-agent-research-system). Haiku moving from low to medium effort halves early stopping at more than double the tokens. — [Haiku 5.5](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/prompting-claude-haiku-5-5)
- **Persistence phrasing that worked:** "You are an agent - please keep going until the user's query is completely resolved… Only terminate your turn when you are sure that the problem is solved." Together with tool-calling and planning reminders, this "increased our internal SWE-bench Verified score by close to 20%". — [GPT-4.1 guide (older, non-Claude)](https://cookbook.openai.com/examples/gpt4-1_prompting_guide)

### Inferences
- **Missing data rule (synthesized; no single source states it in these words):** combine OpenAI's "alternative step if a required piece of info is missing", GPT-4.1's warning that "must" rules cause made-up inputs, and Anthropic's "flag these issues… rather than blindly presenting". In a fan-out brief this becomes: "If a field cannot be found from an acceptable source within budget, write `null` and `status: "not_found"`, list the queries you tried, and do not estimate or fill in from memory unless the field explicitly allows `estimate` with a stated basis." A fixed schema makes "not found" a legitimate, first-class value. Without one, a literal model under "fill every field" pressure is likely to make values up.
- **Budget framing for cheaper models:** give a *range plus a ceiling plus a stop condition*: "Expect about 5–10 searches; stop at 15; stop early once every field has a primary-source value." Avoid "minimize tool calls" (it suppresses searching on Sonnet 5.5). Note that the cookbook's "MINIMUM of five distinct tool calls" floor pushes the other way, against under-searching.
- **Source policy should be domain-specific, not generic.** Name the preferred primary sources (for country data: national statistics offices, central banks, official gazettes, World Bank/IMF/UN datasets). Name a recency window ("prefer data from 2024–2026; record the reference year for every value"). List sources to avoid (aggregators, content farms, AI-generated summaries). This copies the semiconductor "good" example, which names TSMC/Samsung/Intel investor relations pages, SEC EDGAR, SEMI/Gartner/IDC and commerce.gov.
- **Citations and confidence per field:** for a structured fan-out, require `{value, unit, reference_year, source_url, source_type: primary|secondary, confidence: high|medium|low, notes}` per field. That lets the orchestrator check quality mechanically using the MARS rubric dimensions: factual accuracy, citation accuracy, completeness, source quality, tool efficiency.

### Gaps
- No primary source gives measured effects of "say not found" instructions on hallucination rates for Sonnet or Haiku. The recommendation is synthesized.
- No source gives a measured best tool-call budget for Sonnet versus Haiku sub-agents. The budgets above are Anthropic's prompt heuristics from 2025, not tuned per model.

### Takeaway

- **Synthesized fan-out brief template** (my synthesis of the sources above, not a published template):

```
<context>
Today's date: 2026-10-07. Your training data ends before this date; statistics, office holders, laws and rates may have changed, so search for them.
Overall project: <user's goal in 1–3 sentences>. Your result will be merged with ~N parallel agents' results into <final artifact>; consistency of fields and units across agents matters more than prose.
</context>
<task>
Objective (one): For <ENTITY or BATCH of entities>, find <exact fields>.
Why: <what the user will do with it>, so prefer <precision/recency/coverage trade-off>.
Out of scope: <other entities; analysis/opinion; fields not listed; writing a narrative report>.
</task>
<definitions> <field definitions, units, reference-year rule, how to treat territories/disputed cases> </definitions>
<sources>
Prefer: <named primary sources>. Acceptable secondary: <named>. Avoid: aggregators, SEO/content farms, undated pages.
Recency: prefer data from <window>; always record the reference year.
</sources>
<process>
Plan briefly, then search with short queries (<5 words), broad → narrow; fetch full pages for any value you record.

</process>
<missing_data> If a field cannot be confirmed from an acceptable source within budget, set value=null, status="not_found", and list the queries tried. Never estimate or fill from memory. If sources conflict, report both with URLs. </missing_data>
<output>
Return ONLY this JSON (one object per entity) [or write it to <path> and return the path + a 3-line summary]:
{ "entity": "...", "fields": { "<field>": {"value":..., "unit":"...", "year":..., "source_url":"...", "source_type":"primary|secondary", "confidence":"high|medium|low", "status":"found|not_found|conflict", "notes":"..."} }, "queries_tried": [...], "open_issues": [...] }
<example> one complete, realistic filled object incl. one not_found field </example>
Before returning, check: every listed field present; every non-null value has a URL and a year; no values from memory.
</output>
Keep working until every field is resolved or marked not_found; then stop and report. Don't add fields or commentary that weren't asked for.
```

- **Before → after for the user's job.** Before: "Research <Country>'s <topic> and report back." After: the template above, with the field list and definitions written once by the orchestrator and pasted identically into every brief, plus a country-specific line where relevant ("For <Country>, the statistics office is <X>"). Identical definitions and schema across briefs address Cognition's "conflicting implicit decisions" problem, where each agent picks its own units, years and interpretations.

## 6. Self-contained briefs: what context must be passed explicitly, and how long a brief should be

### Takeaway
Yes. A brief must be fully self-contained. Claude Code sub-agents start with a fresh context and see only their system prompt, the delegation message, CLAUDE.md, a git status snapshot and any preloaded skills. They do *not* see the conversation, files already read, skills already invoked, output style or memory. Pass the user's goal and why, definitions, the date, format conventions, prior decisions and any rule that must hold. Length should be "minimal but sufficient": dense, sectioned, and typically a few hundred words. The evidence also shows long prompts hurting cheaper models (early stopping, skipped searches, lost rules).

### Cited Findings
- "Each subagent starts with a fresh, isolated context window. It doesn't see your conversation history, the skills you've already invoked, or the files Claude has already read. Claude composes a delegation message that summarizes the task, and the subagent works from there." The exception is a fork. — [Claude Code subagents docs](https://code.claude.com/docs/en/sub-agents)
- What a non-fork sub-agent does receive: its own system prompt plus environment details, "Task message: the delegation prompt Claude writes when it hands off the work", CLAUDE.md files (except for Explore/Plan or with `omitClaudeMd`), a git status snapshot, preloaded skills, and a sibling roster. What it does not receive: output style, auto memory. Its "context window is sized by its own model". — [Claude Code subagents docs](https://code.claude.com/docs/en/sub-agents)
- "If a rule must [reach the subagent], such as 'ignore the `vendor/` directory,' restate it in the prompt you give Claude when delegating." — [Claude Code subagents docs](https://code.claude.com/docs/en/sub-agents)
- **Cognition, Principle 1:** "Share context, and share full agent traces, not just individual messages." **Principle 2:** "Actions carry implicit decisions, and conflicting decisions carry bad results." In the Flappy Bird example, one sub-agent built a "Super Mario Bros" background, and even with shared context the parallel agents produced "a bird and background with completely different visual styles". The post warns that "most real-world tasks have many layers of nuance that all have the potential to be miscommunicated." — [Cognition, Don't Build Multi-Agents (2025)](https://cognition.ai/blog/dont-build-multi-agents)
- **Small models misread large-model instructions:** in "edit apply" pipelines, "the small model would misinterpret the instructions of the large model and make an incorrect edit due to the most slight ambiguities in the instructions." — [Cognition](https://cognition.ai/blog/dont-build-multi-agents)
- **Why Claude Code limited subagents (as of mid-2025):** "The subtask agent lacks context from the main agent that would otherwise be needed to do anything beyond answering a well-defined question." — [Cognition](https://cognition.ai/blog/dont-build-multi-agents)
- The lead prompt requires "Relevant background context about the user's question and how the subagent should contribute to the research plan". — [research_lead_agent.md](https://github.com/anthropics/claude-cookbooks/blob/main/patterns/agents/prompts/research_lead_agent.md)
- Vague guidance that "falsely assumes shared context" is named as a failure mode. — [Context engineering](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)
- **Length evidence:** Anthropic's own "good" brief is a single paragraph of about 150 words. — [research_lead_agent.md](https://github.com/anthropics/claude-cookbooks/blob/main/patterns/agents/prompts/research_lead_agent.md). The lead is told "describe everything needed in the fewest words possible". — same source. "Minimal does not necessarily mean short". — [Context engineering](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents). For Haiku 5.5, skipped searches happen "most at `low` effort and with long system prompts", and early stopping appears with "a long coding-agent system prompt at `low` effort" but rarely with a short one. — [Haiku 5.5](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/prompting-claude-haiku-5-5). Rules "getting lost" in long files. — [Claude Code best practices](https://code.claude.com/docs/en/best-practices)
- **Model selection practice:** "build your agent prototype with the most capable model for every task to establish a performance baseline. From there, try swapping in smaller models to see if they still achieve acceptable results… diagnose where smaller models succeed or fail." — [OpenAI practical guide](https://cdn.openai.com/business-guides-and-resources/a-practical-guide-to-building-agents.pdf)

### Inferences
- **Context that must be passed explicitly in every fan-out brief:** today's date and the recency window; the user's end goal and how this piece feeds it; exact entity identity (for example, "Georgia = the country, not the US state"; which list defines "country"); field definitions, units, currency and reference-year conventions; the output schema and file path; source policy; budget and stop rule; the missing-data convention; and any user-stated constraints the orchestrator heard in conversation (CLAUDE.md is loaded, but conversation-only instructions are not).
- **Cognition's "share full traces" advice does not fit a 195-way research fan-out** (too many tokens, and the tasks are independent reads). The workable adaptation is to share *decisions*, not traces: one canonical definitions-and-schema block, written once and reused verbatim in every brief, so no sub-agent has to make an implicit decision another agent might make differently.
- **Length heuristic (synthesized):** roughly 300–800 words for a structured data-gathering brief. That is enough to carry the definitions, schema, one example and the policies, while staying well short of the long prompts that degraded Haiku and Sonnet at low effort. The orchestrator should test whether a colleague with no context could carry out the brief, using the docs' "golden rule".

### Gaps
- No source measured brief length against sub-agent quality directly. The Haiku evidence is about long *system* prompts in agent harnesses, so applying it to task-message length is an inference.

## 7. Evidence on few-shot examples, checklists and step-by-step procedures for cheaper models

### Takeaway
Anthropic and OpenAI both recommend examples and explicit steps, and several model-specific Anthropic tests show prompt additions measurably improving Sonnet and Haiku behavior. Academic evidence on whether *smaller* models benefit more from few-shot examples is mixed and task-dependent; one 2026 study found a single example rescued an 8B model while extra examples hurt a 17B model. Practical guidance: include one or two complete, realistic output examples (including a "not found" case), tell the model to vary content and not copy example values, and use numbered steps for the process and a checklist for self-verification. Avoid long edge-case lists.

### Cited Findings
- Anthropic recommends 3–5 relevant, diverse, tagged examples ("one of the most reliable ways to steer Claude's output format, tone, and structure"). — [Prompting best practices](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/claude-prompting-best-practices)
- "Providing examples, otherwise known as few-shot prompting, is a well known best practice that we continue to strongly advise", using "diverse, canonical examples" rather than an edge-case laundry list. — [Context engineering](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)
- For Sonnet 5, positive examples beat negative instructions for controlling verbosity. — [Prompting Claude Sonnet 5](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/prompting-claude-sonnet-5)
- **Example over-copying:** "When provided sample phrases, models can use those quotes verbatim and start to sound repetitive… instruct the model to vary them as necessary." — [GPT-4.1 guide (older, non-Claude)](https://cookbook.openai.com/examples/gpt4-1_prompting_guide)
- **Step-by-step:** "Providing smaller, clearer steps from dense resources helps minimize ambiguity and helps the model better follow instructions." — [OpenAI practical guide](https://cdn.openai.com/business-guides-and-resources/a-practical-guide-to-building-agents.pdf). "Provide instructions as sequential steps using numbered lists… when the order or completeness of steps matters." — [Prompting best practices](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/claude-prompting-best-practices)
- **Measured prompt-induced planning:** "inducing explicit planning increased the pass rate by 4%" (GPT-4.1, SWE-bench Verified). The three agentic reminders together gave "close to 20%". — [GPT-4.1 guide (older)](https://cookbook.openai.com/examples/gpt4-1_prompting_guide)
- **Measured on Sonnet 5.5:** adding "Think the problem through before you answer." brings accuracy at `high` effort "close to what the model reaches at `xhigh`". At low and medium it "raises accuracy, though not to what the model reaches at `high`." — [Prompting Claude Sonnet 5.5](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/prompting-claude-sonnet-5-5)
- **Measured on Haiku 5.5:** the search nudge raised search rate on changed-fact questions, with 0–3% unneeded searches. The JSON line "raised the share of complete and correct JSON answers at `low` and `medium` effort". The verification paragraph meant "the model checked its changes more often… and its performance improved". — [Haiku 5.5](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/prompting-claude-haiku-5-5)
- **Checklists in Anthropic's own subagent template:** the code-reviewer subagent uses a numbered "When invoked" procedure plus an 8-item "Review checklist" and a fixed, prioritized output structure. — [Claude Code subagents docs](https://code.claude.com/docs/en/sub-agents)
- **Counterweight against rigid procedures:** Anthropic warns against "hardcoding complex, brittle logic". — [Context engineering](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents). It prefers "good heuristics rather than rigid rules". — [Anthropic](https://www.anthropic.com/engineering/multi-agent-research-system)
- **Academic few-shot evidence (mixed):** Dwivedi & Soni (arXiv 2607.22969, Jul 2026) tested 5 LLMs at 0–8 shots on AG News. They found the shot-count/performance relationship is "neither monotonic nor universal" and cannot be predicted from scale. Llama 3.1 8B collapsed at zero-shot but recovered sharply with one example (Cohen's d = 10.98). Llama 4 Scout 17B was best at zero-shot and degraded with more examples. An output-parsing artifact understated Llama 3.3 70B by up to 206%. (Read via WebFetch summary of the abstract.) — [arXiv 2607.22969](https://arxiv.org/abs/2607.22969)
- **Older and snippet-level studies (not verified in full):** SMASH (EMNLP Findings 2022) reports that prompts brought small models fewer improvements than larger ones — [ACL Anthology](https://aclanthology.org/2022.findings-emnlp.492/). A 2022 study found extra demonstrations "disproportionately" helped larger models — [arXiv 2212.01907](https://arxiv.org/pdf/2212.01907). By contrast, an idiomaticity study reported the smallest models "benefited the most from seeing one or more examples" — [arXiv 2405.09279](https://arxiv.org/pdf/2405.09279).

### Inferences
- For *format and schema compliance* (the main fan-out problem), one or two complete examples are cheap and well supported. For *content*, examples carry a copying risk. Use clearly fictional or placeholder values, or an example from a different entity, and add "values are illustrative; do not reuse them".
- Include a "not_found" field in the example. Without it, the example teaches that every field always gets a value. This follows from Sonnet's literalism and from the copying failure mode.
- Checklists work best as a **pre-return self-check** (fields present, URL and year on every value, nothing from memory), which closes the "looks done" gap from the Claude Code best practices. Rigid step-by-step search scripts per country would fall into the "brittle logic" failure. Give the process as heuristics (broad then narrow, fetch full pages, prefer primary sources) and the output requirements as hard rules.
- Because results vary with model and task (the 2026 study), the skill should recommend a small pilot: run 5–10 representative entities, grade with the MARS rubric, fix the brief, then fan out. Anthropic reports early prompt tweaks moving success "from 30% to 80%" on about 20 test queries.

### Gaps
- No published Anthropic experiment directly compares few-shot versus zero-shot *sub-agent briefs* on Sonnet or Haiku. The cheaper-model gains cited are from system-prompt lines in Anthropic's testing, not from delegation-message experiments.
- Practitioner write-ups (Simon Willison, Hamel Husain, Eugene Yan) specifically on writing sub-agent briefs were not found or read within budget. This is a gap rather than an absence of such material.
